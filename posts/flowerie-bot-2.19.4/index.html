🌸 花璃 v2.19.4 更新公告

这轮没加功能，做的是尺子。

你要把花璃搬到树莓派上，但「能不能跑」这种事不该靠感觉——所以我把它全测了一遍， 测出来的东西都写成了脚本，你换机器可以自己再跑一遍对比。

📏 一、五个脚本，五种问法

| 脚本 | 回答什么问题 | 跑多久 | | :--- | :--- | :--- | | bench.py | 单个操作有多快 | 1 分钟 | | bench_load.py | 多群群聊能扛多少 | 1 分钟 | | bench_stress.py | 所有功能同时开会怎样 | 90 秒 | | bench_resources.py | 除了 CPU 内存还吃什么 | 20 秒 | | bench_gpu.py | 到底用不用 GPU | 1 秒 |

都能 --json，方便拿两台机器的输出直接对比。

⚡ 二、先说结论：本地开销可以忽略

一条群消息的本地处理链——@ 检测 → 文本消毒 → 分句——0.128 毫秒。

而一次 LLM 往返要 1000~5000 毫秒。

总延迟 ≈ 10ms（网络） + 1500ms（LLM） + 0.13ms（花璃本地）
                                    ↑ 占 0.009%

本地处理再慢 20 倍也不到 2.5 毫秒。

这是树莓派能跑的根本原因——花璃不是计算密集型，是 IO 等待型（等 API 返回）。

📊 三、负载五档：真实场景离极限很远

| 档位 | 群数×速率 | 附件 | 实际吞吐 | p95 | CPU | RSS | | :--- | :--- | :--- | ---: | ---: | ---: | ---: | | 轻载 | 1×1/s | 无 | 1.0 msg/s | 15.5 ms | 0% | 70 MB | | 日常 | 5×2/s | 2%/5%/2% | 10.0 msg/s | 3.5 ms | 1% | 70 MB | | 繁忙 | 10×5/s | 5%/10%/5% | 49.6 msg/s | 6.6 ms | 6% | 70 MB | | 压力 | 30×10/s | 10%/20%/10% | 294 msg/s | 8.3 ms | 46% | 71 MB | | 极限 | 50×20/s | 10%/25%/10% | 947 msg/s | 11.3 ms | 78% | 71 MB |

10 个群最繁忙也就 10~20 msg/s（受 LLM 往返限制）。实测 50 msg/s 只用 6% 单核， 余量超过 15 倍。

内存从 1 群到 50 群、从 1 到 947 msg/s，全程 70~71 MB，一点没涨。

因为消息处理是「进来→处理→丢弃」的无状态流水线，不积累。

🔥 四、全功能压测：9 个子系统同时跑

前面测的是「某个功能多快」，这里测「全都开着会不会崩」。

消息链 / 文档解析 / 图片转码 / UI 渲染 / SQLite / 记忆写入 / 表情索引 / 插件往返 / 摘要拼装—— 9 路同时满速，最高开到 6 倍并发：

| 档位 | 总吞吐 | 错误 | CPU | RSS | | :--- | ---: | ---: | ---: | ---: | | x1 | 743 ops/s | 0 | 67% | 74 MB | | x3 | 1080 ops/s | 0 | 74% | 74 MB | | x6 | 1138 ops/s | 0 | 70% | 75 MB |

76000+ 次操作，零错误。 SQLite 没有 database is locked，asyncio 没有阻塞告警。

有意思的是并发从 3 路加到 6 路，吞吐只涨 5%，CPU 停在 70%—— 这是单核饱和，Python 的 GIL 让所有 CPU 活排在一个核上。

还有一个现象：文档解析的 p95 从 16ms（x1）涨到 74ms（x3）再到 159ms（x6）。 延迟涨了 10 倍，吞吐只涨 55%。这是教科书级的队列饱和。

但真实场景不需要担心：一个群同时来 6 份文档的概率基本为零。

💾 五、SD 卡会不会写坏？

这是我原本最担心的。实测：

真实速率（20 msg/min）= 25.8 KB / 条消息
每天活跃 8 小时 ≈ 242 MB/天 ≈ 86 GB/年

128GB TLC 卡（标称 100 TBW，写入放大 2x）→ 约 594 年。

就算按 3 倍保守估（还有配置、画像、知识库、日志），也是几十年。

SD 卡不会因为写入量写坏。 真正的问题是写入延迟—— 花璃默认 synchronous=FULL（每次都 fsync），内存盘上 3.4ms，换 SD 卡可能 50~200ms。

慢盘上建议改：

PRAGMA synchronous = NORMAL;

WAL + NORMAL 下崩溃最多丢最后几条事务，不会损坏库，写入延迟从百毫秒降到个位数。

还有个好消息：空闲时零写入。静置 5 秒，磁盘写入 0 MB，write 系统调用 0 次。 没有心跳写盘。

🎮 六、GPU 这条：测不了，所以我去证了

你问「Web UI 不需要 GPU 吗」，我想直接测，结果发现三条路全堵：

  • Mali 的 /sys/class/misc/mali0/device/utilization → 不存在
  • /sys/kernel/debug → 要 root
  • dumpsys SurfaceFlinger → 权限拒绝

根因是：Linux 没有进程级 GPU 统计。CPU 和内存是进程隔离的，GPU 是全局资源， 内核对「某个进程用了多少 GPU」这件事压根没概念。

所以换个思路：既然测不了用量，就证明根本没有调用路径。

[1] 代码层  cairo/skia/opengl/vulkan/webgl 引用     0 处
[2] 链接层  libGL/libEGL/libGLESv2/libvulkan 加载   0 个
[3] 驱动层  GPU 设备节点是否被打开
            系统存在: /dev/mali0, /dev/dri/card0
            本进程打开: 无
[4] 线程层  渲染线程                                0 个（全进程 1 线程）

结论：GPU 零路径

第 3 项特别有说服力——这台机器确实有 Mali GPU，设备节点也在，但花璃进程连 fd 都没开过。

这比「占用 0.1%」强得多：低占用还可能波动，零路径是结构性的。

顺带澄清：Web UI 的图形在打开页面的人的设备上渲染，不在服务器。 服务端只做一件事——拼 15 KB 的 HTML 字符串，3.06 毫秒。

⚠️ 七、一个坑：必须装 64 位系统

测资源时发现 VMS 是 10,850 MB，吓了一跳。查了才知道：

空 Python 进程 VmSize: 10,830 MB
实际 RSS:                 43 MB   ← 才是真占用

Python 3.14 在 64 位系统上会预留极大的虚拟地址空间，这是 arena 分配策略，不是内存占用。

但这条有个实际后果：32 位系统的地址空间只有 4 GB，解释器起不来。

所以树莓派必须装 64 位系统。Pi 4/5 的 64 位 Pi OS 没问题，Pi 3 装 32 位就会踩。

🍓 八、树莓派怎么选

| 机型 | 极限吞吐 | 10 群真实负载 | 内存 | 判断 | | :--- | ---: | :--- | :--- | :--- | | Pi 5 | ~1250 ops/s | CPU <10% | 4~8 GB | ✅ 充裕 | | Pi 4 | ~620 ops/s | CPU <20% | 2~4 GB | ✅ 推荐 | | Pi 3B+ | ~285 ops/s | CPU <35% | 1 GB | ⚠️ 别装重插件 | | Zero 2 W | ~140 ops/s | CPU 约 35% | 512 MB | ❌ 会 OOM |

Pi 4 (2GB) 就够了。 记住配合：

  • USB 3.0 SSD 启动（或至少 A2 级 microSD）
  • 64 位系统
  • 慢盘上改 synchronous=NORMAL
